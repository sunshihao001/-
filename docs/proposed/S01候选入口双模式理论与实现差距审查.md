## 0. 审查结论

`meme-candidate-entry` 的理论基础已经存在，而且不是空壳。

现有理论核心是：

```text
GMGN 字段 = 入口材料
GMGN 标签 = hint
字段组合 = 候选入口判断地基
链上行为规则 = 最终判断依据
```

S01 的阶段目标不是判断能不能买，而是判断：

```text
这个 token / 这批 token 是否值得进入完整 S02-S06 深度分析流程。
```

当前最重要的产品决策已确认：

```text
S01 采用双模式：
manual mode：宽进，重提示。
batch mode：严筛，省资源。
```

也就是说，同一套五力理论在两种模式下用法不同：

```text
manual mode：五力主要作为 caution layer。
batch mode：五力可以作为 filter layer。
```

## 1. S01 阶段目标

S01 是候选入口，不是最终交易门控。

它的下游是：

```text
S02 meme-token-panel
S03 meme-wallet-roles
S04 meme-wallet-structure
S05 meme-evidence-chain
S06 meme-trade-gate
```

所以 S01 只回答入口问题：

```text
这个对象是否值得继续分析？
```

S01 不回答：

```text
这个 token 是否可以买？
这个 token 是否一定危险？
这个 token 是否确定由某类钱包控制？
这个 token 是否应该触发交易动作？
```

S01 的专业定位：

```text
Candidate Entry Gate / Entry-layer Resource Allocation Gate
```

中文可称：

```text
候选入口资源分配门
```

## 3. 核心理论：五力模型

S01 的总模型：

```text
候选价值 = 承接力 × 扩散力 - 控制力 - 伪装力 - 退出力
```

注意：这不是交易公式。

它是候选入口阶段的判断框架。

---

## 4. 五力之一：承接力

### 4.1 核心问题

```text
市场能不能接住买卖？
```

### 4.2 主要字段

```text
liquidity
market_cap
volume
swaps
buys
sells
volume / liquidity
liquidity / market_cap
```

### 4.3 理论逻辑

meme token 的短期价格必须依赖流动性承接。

如果流动性太低：

- 少量买入能拉高。
- 少量卖出能砸穿。
- 价格信号不稳定。
- 后续钱包结构分析容易被少数钱包污染。

如果市值太低：

- 仍处于噪声区。
- 价格容易被单钱包行为主导。
- 交易样本不足。

### 4.4 典型判断

```text
市值高 + 流动性低
= 账面估值高，实际承接弱
= 估值虚胖
```

```text
市值低 + 流动性低
= 噪声区
= batch mode 可过滤
```

```text
市值和流动性同步增长
= 市场承接开始形成
= 值得进入二段筛选
```

### 4.5 建议输出

```json
{
  "absorption_power": "weak | normal | strong | unknown",
  "liquidity_quality_hint": "thin | healthy | overheated | unknown",
  "valuation_liquidity_relation": "matched | inflated | early_pool | unknown"
}
```

---

## 5. 五力之二：扩散力

### 5.1 核心问题

```text
参与是否从少数地址扩展到更多地址？
```

### 5.2 主要字段

```text
holder_count
swaps
buys
sells
volume
smart_degen_count
renowned_count
bluechip_owner_percentage
swaps / holder_count
```

### 5.3 理论逻辑

meme token 想持续，必须发生扩散。

真实扩散表现为：

- holder_count 增长。
- swaps 增长。
- buys / sells 都有。
- 交易地址变多。
- top_10_holder_rate 下降或稳定。

控制扩散表现为：

- holder_count 看起来增长。
- top_10_holder_rate 仍高。
- 交易来自少数地址。
- bundler_rate 高。
- sniper_count 高。

关键关系：

```text
swaps / holder_count
```

如果 swaps 很高但 holder_count 很低，可能是：

- 少数地址反复交易。
- 机器人刷成交。
- 市场参与没有真正扩散。

### 5.4 建议输出

```json
{
  "diffusion_power": "weak | growing | broad | unknown",
  "activity_distribution_hint": "broad | concentrated | bot_like | unknown"
}
```

## 6. 五力之三：控制力

### 6.1 核心问题

```text
这个盘是否被少数钱包、开发者或机器人控制？
```

### 6.2 主要字段

```text
top_10_holder_rate
bundler_rate
sniper_count
creator_token_status
creator_close
dev_token_burn_ratio
```

### 6.3 理论逻辑

控制力强，说明少数主体可能影响价格、制造走势、决定退出节奏。

控制力来源：

1. 筹码控制。
2. 早期进入控制。
3. 批量地址控制。
4. 开发者控制。

S01 不能输出确定性结论，只能输出疑似结构 hint。

### 6.4 建议输出

```json
{
  "control_power": "low | medium | high | unknown",
  "control_reasons": []
}
```

## 7. 五力之四：伪装力

### 7.1 核心问题

```text
热度、成交、社交是否可能被制造？
```

### 7.2 主要字段

```text
is_wash_trading
image_dup
twitter_change_flag
twitter_rename_count
twitter_del_post_token_count
twitter_create_token_count
rat_trader_amount_rate
dexscr_boost_fee
hot_level
```

### 7.3 理论逻辑

meme 市场里很多信号都可以被制造：

- 成交量。
- 持有人数量。
- 社交热度。
- K 线形态。
- 短期涨幅。
- GMGN 热榜位置。

所以 S01 不能因为热就通过，要判断热度是否有伪装痕迹。

### 7.4 建议输出

```json
{
  "camouflage_power": "low | medium | high | unknown",
  "narrative_shell_risk": "low | medium | high | unknown"
}
```

## 8. 五力之五：退出力

### 8.1 核心问题

```text
早期参与者是否有能力或动机砸盘退出？
```

### 8.2 主要字段

```text
creator_close
creator_token_status
top_10_holder_rate
liquidity / market_cap
dev_token_burn_ratio
renounced_mint
renounced_freeze_account
sell_volume
price_change_percent
rat_trader_amount_rate
bundler_trader_amount_rate
```

### 8.3 理论逻辑

meme token 最大的结构风险是退出。

早期主体关心：

```text
能不能把筹码卖给后来者？
```

后来者关心：

```text
自己会不会成为退出流动性？
```

退出力强的组合：

```text
top_10_holder_rate 高
liquidity / market_cap 低
creator 风险高
dev token 未处理
权限未放弃
```

含义：

```text
早期主体具备砸盘能力，市场承接能力不足，后续参与者容易成为退出流动性。
```

### 8.4 建议输出

```json
{
  "exit_power": "low | medium | high | unknown",
  "exit_risk_reasons": []
}
```

## 11. Manual mode：手动 CA 分析入口

### 11.1 场景

用户主动给一个 token address，让系统分析。

### 11.2 核心原则

```text
宽进，重提示，不轻易挡住。
```

因为用户已经指定 token，此时 S01 不应过早替后续阶段下结论。

### 11.3 S01 只在这些情况下 STOP

```text
地址无效
token 不存在
无交易池
零流动性
GMGN token info 完全失败
```

这些不是交易判断，而是对象不可分析。

### 11.4 其他风险的处理

如果出现：

- 风险密度高。
- 承接力弱。
- 扩散力弱。
- 控制力高。
- 伪装力高。
- 退出力高。
- 部分字段缺失。

manual mode 应该：

```text
输出 CAUTION / UNKNOWN。
继续进入完整 S02-S06。
```

### 11.5 推荐输出行为

```json
{
  "mode": "manual",
  "basic_gate": {
    "decision": "PASS | UNKNOWN | FILTERED_OUT",
    "reasons": []
  },
  "entry_aux_decision": "PASS | CAUTION | UNKNOWN",
  "next_action": "RUN_FULL_WORKFLOW | RUN_FULL_WORKFLOW_WITH_CAUTION | STOP"
}
```

---

## 12. Batch mode：批量候选池筛选入口

### 12.1 场景

系统从 GMGN trending / trenches / signal 拉一批 token。

### 12.2 核心原则

```text
严筛，省资源，避免低质量 token 消耗 S02-S06。
```

### 12.3 可以过滤的情况

```text
流动性低
市值低
volume 不足
holder_count 太少
swaps 太少
风险密度 extreme
承接弱 + 扩散弱 + 控制高
承接弱 + 退出力高
伪装力高 + 扩散弱
```

### 12.4 缺字段处理

如果关键字段缺失，不应伪造通过，也不应填默认值。

应输出：

```text
basic_gate = UNKNOWN
force = unknown
missing_fields = [...]
```

是否进入后续流程，由 batch 参数和 controller 决定。

### 12.5 推荐输出行为

```json
{
  "mode": "batch",
  "basic_gate": {
    "decision": "PASS | FILTERED_OUT | UNKNOWN",
    "reasons": []
  },
  "entry_aux_decision": "PASS | CAUTION | SKIP | FILTERED_OUT | UNKNOWN",
  "next_action": "RUN_FULL_WORKFLOW | RUN_FULL_WORKFLOW_WITH_CAUTION | STOP"
}
```

## 13. 五力在双模式下的用法差异

### 13.1 承接力

manual mode：

```text
低承接力 → CAUTION，继续跑。
零流动性 / 无池子 → STOP。
```

batch mode：

```text
低承接力 → FILTERED_OUT。
```

### 13.2 扩散力

manual mode：

```text
扩散弱 → CAUTION，继续跑。
```

batch mode：

```text
扩散弱 → FILTERED_OUT 或 UNKNOWN。
```

### 13.3 控制力

manual mode：

```text
控制力高 → CAUTION，继续跑 wallet-roles / wallet-structure。
```

batch mode：

```text
控制力高 → CAUTION；若叠加承接弱 / 扩散弱，可 SKIP 或 FILTERED_OUT。
```

### 13.4 伪装力

manual mode：

```text
伪装力高 → CAUTION，继续跑 evidence-chain。
```

batch mode：

```text
伪装力高 + 扩散弱 → SKIP / FILTERED_OUT。
```

### 13.5 退出力

manual mode：

```text
退出力高 → CAUTION，继续跑 trade-gate。
```

batch mode：

```text
退出力高 + 承接弱 → SKIP / FILTERED_OUT。
```

## 14. Frozen specs 合约

`docs/specs.md` 已经规定 S01 必须输出：

```json
{
  "entry_stage": "candidate_entry",
  "basis": "gmgn_field_combination_hint",
  "basic_gate": {
    "decision": "PASS | FILTERED_OUT | UNKNOWN",
    "reasons": []
  },
  "five_forces": {
    "absorption_power": "weak | normal | strong | unknown",
    "diffusion_power": "weak | growing | broad | unknown",
    "control_power": "low | medium | high | unknown",
    "camouflage_power": "low | medium | high | unknown",
    "exit_power": "low | medium | high | unknown"
  },
  "gmgn_risk_density": {
    "level": "low | medium | high | extreme | unknown",
    "score": 0.0,
    "reasons": []
  },
  "entry_aux_decision": "PASS | CAUTION | SKIP | FILTERED_OUT | UNKNOWN",
  "next_action": "RUN_FULL_WORKFLOW | RUN_FULL_WORKFLOW_WITH_CAUTION | STOP"
}
```

关键规则：

1. `basis` 必须是 `gmgn_field_combination_hint`。
2. 五力输出只是 hint layer，不是最终链上结论。
3. `entry_aux_decision` 不替代 `meme-trade-gate.gate_decision`。
4. `basic_gate.decision == FILTERED_OUT` 时，`next_action = STOP`。
5. batch 可 short-circuit。
6. single-token run 必须继续完整流程，只能加 `CAUTION`。
7. 阈值和分类逻辑必须在 `rules/entry_five_forces_rules_v1.json`，不能硬编码在代码里。
8. GMGN 标签不能作为 hard gate。

## 16. 理论与实现差距

### 16.1 差距一：输出合约未完全对齐 specs

理论 / specs 要求输出：

```text
entry_stage
basis
basic_gate
five_forces
gmgn_risk_density
entry_aux_decision
next_action 新语义
```

当前代码主要还是旧结构：

```text
status
initial_validation
evidence
confidence_score
downgrade_reasons
blocker_reasons
missing_fields
valid_until
next_action
handoff_to
```

旧字段不一定要删，但必须补齐 specs 字段。

### 16.2 差距二：双模式语义需要显式化

当前代码有两个入口：

```text
run(...)
build_candidate_pool(...)
```

但需要明确：

```text
run = manual mode
build_candidate_pool = batch mode
```

并且两者的 STOP / CAUTION / FILTERED_OUT 语义不同。

### 16.3 差距三：阈值可能还存在硬编码

`build_candidate_pool(...)` 当前可见参数包含：

```python
min_liquidity = 50000
min_market_cap = 50000
```

但 specs 要求：

```text
Field thresholds and force-classification logic MUST live in machine-loadable rules/entry_five_forces_rules_v1.json, not in code constants.
```

所以后续需要改为从 `rules/entry_five_forces_rules_v1.json` 加载阈值。

### 16.4 差距四：五力计算应由规则文件驱动

`rules/entry_five_forces_rules_v1.json` 已有完整五力定义。

后续实现应避免把五力分类逻辑散落到代码里。

代码应该负责：

```text
读取规则 → 读取字段 → 计算派生指标 → 生成 force level → 写出 reasons。
```

不应负责：

```text
在代码里重新发明业务规则。
```

### 16.5 差距五：S01 缺 SKILL.md

当前目录：

```text
skills/meme-candidate-entry/
```

缺：

```text
SKILL.md
```

这会影响 Hermes skill 形态完整性。

后续应从本审查文档、specs、rules、设计文档反推 `SKILL.md`。

## 17. 需求澄清问题

后续写代码或任务卡前，PM 需要继续确认：

### Q1. Manual mode 是否只在基础不可分析时 STOP？

建议答案：是。

基础不可分析包括：

```text
地址无效
token 不存在
无池子
零流动性
GMGN token info 完全失败
```

其他风险只 CAUTION。

### Q2. Batch mode 的 FILTERED_OUT 是否保存 candidate record？

建议答案：必须保存。

原因：过滤也是结果，需要可审计。

### Q3. UNKNOWN 在 batch mode 下是否继续跑？

需要决策。

建议：默认不跑完整 S02-S06，但保存 UNKNOWN；除非用户显式要求 deep scan unknowns。

### Q4. `status` 字段是否继续保留？

建议：保留兼容旧链路，但新增 specs 字段为主。

旧字段：

```text
status = PASS / BLOCK / WARN / ERROR
```

新字段：

```text
basic_gate.decision
entry_aux_decision
next_action
```

### Q5. `entry_aux_decision == SKIP` 在 manual mode 是否禁止？

建议：manual mode 不输出 SKIP，只输出 CAUTION / UNKNOWN / PASS / STOP。

### Q6. risk density high / extreme 在 batch mode 的行为？

建议：

```text
high = CAUTION
extreme = SKIP 或 FILTERED_OUT
```

但不能仅凭单个黑箱标签 extreme，必须是风险密度组合。
